A table renderer can save work by dropping a column, skipping a conditional cell, or copying a value without escaping it. The result can look plausible at a glance. A benchmark needs to verify what the renderer actually produced before assigning a time to it.

## Compare the parsed page

For canonical SSR, Chromium parses each adapter’s HTML output. The harness compares the resulting document structure, attributes, class tokens, and visible text. The fixtures exercise escaping, branches, loops, and number and date formatting so that those checks cover work a real template has to do.

The harness allows specific differences such as class-token ordering and internal hydration comments. It records response bytes and exact-byte equality separately. Disclosed adaptations have their own documented checks.

## Test the check itself

Each canonical workload also has a negative control. The harness deliberately changes something meaningful in the output and requires the comparison to reject it. A failed parity check stops the run before timing begins.

## Inspect a fixture yourself

Open the [product grid comparison](/?section=performance&view=rendering&workload=products) to preview the shared fixture. Its 96 cards include prices, ratings, and repeated SVG stars.
